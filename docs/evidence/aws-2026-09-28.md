## Failure and fixes

The [failed-step log](aws-2026-09-28-deploy-failed.txt), read before any source change,
ends with `Not authorized to perform sts:AssumeRoleWithWebIdentity` at 17:50:10.231 UTC.
Trailing whitespace is normalized in the text export; the recording preserves the original.
A read-only request to `repos/Aly700/capstan/actions/oidc/customization/sub` returned:

```json
{"use_default":true,"use_immutable_subject":true,"sub_claim_prefix":"repo:Aly700@112176329/capstan@1392801248"}
```

The deployed role required `repo:Aly700/capstan:ref:refs/heads/main`. Its audience and
branch were correct, but its subject omitted both IDs. Repository metadata independently
confirmed owner ID `112176329` and repository ID `1392801248`. The fix uses the exact
returned prefix followed by `:ref:refs/heads/main`, retaining `StringEquals` and the
`sts.amazonaws.com` audience. GitHub documents this
[immutable subject format](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims).
The regression failed against the old template and passed after the one-line trust fix.
This fix is verified in synthesized templates; successful live authentication is pending.

The same run warned that `aws-actions/configure-aws-credentials@v4` ignores
`allowed-account-ids`. The second fix keeps the pinned action and adds an explicit
`aws sts get-caller-identity` comparison with `AWS_ACCOUNT_ID` before any image or
resource operation. Tests proved that a wrong account and an STS error both stop after
that one identity request. The previous script incorrectly continued with a wrong account.
